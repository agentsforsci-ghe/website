Literacy

What you need to know before you can use the output

You have to be able to judge the output

Every model produces some defective output. Useful use therefore requires enough expertise to tell good output from bad. The person, not the model, is what makes the output usable.

Cory Doctorow’s corollary is uncomfortable and worth stating plainly: a student is by definition not yet an expert in the subject, so learning a subject from a chatbot is incoherent. An expert can use the tool to generate and validate material precisely because they can accept or reject what comes back.

For this workshop, the practical reading is that the agent is most useful on work you could have done yourself but would rather not, and least trustworthy exactly where you cannot check it.

The question that matters

The anchor story from academic libraries: a student brought a polished outline generated by a chatbot and asked, “How do I know if this is actually right?”

That is the right question, and answering it is a skill separate from producing the output. AI literacy is an extension of information literacy: where did this come from, can I verify it, does it support my work.

Citation literacy is worth separating from citation mechanics here. Reference managers already showed that automating the format can hide whether anyone understood the source. Citation is about transparency and honesty; formatting was never the purpose.

On detection: AI text detectors cannot reliably identify AI-written text, and building integrity policy on them does not work. The better design is work where people demonstrate their thinking through drafts, process, and transparency about what they used, which is what a version-controlled workflow produces anyway.

Skills erode when you outsource them

Skill retention drops when the tool does the work. Vicki Boykis’s proposed remedy is deliberate friction, for example reading every diff the agent produces. Her formulation: we should be more tired than the model.

This is not an argument against using agents. It is an argument for choosing where the friction goes. Reading the diff is slower than accepting it, and that slowness is where the understanding lives.

Write down what you know about your data

If you use an agent for data analysis, you have to write down what you know about the data so the agent can help. Hadley Wickham’s point is that this is not new work invented for machines: the data dictionary is the same documentation that always helped human colleagues, and mostly did not get written.

His working method keeps three things in sync: the cleaning script, a data dictionary, and the data file itself, with a commit after each AI-assisted edit.

The workshop tests this directly. The same agent gets a plain CSV, then gets the same data published as a documented data package. The difference in what it can do is the argument for documentation, made empirically rather than asserted.

Where are you now

The Reproducibility Levels framework describes five levels, from ephemeral work at one end to full reproducibility at the other, with a realistic middle target: a version-controlled workflow that a close collaborator could rerun.

You will locate your own practice on it during the day, per dimension (version control, workflow, environment). A mixed profile is normal and expected. The useful output is not the label but the next step from where you actually are.

NoteThe short version

The agent is a lever, not a substitute for knowing your field. It works best where you could check it and worst where you cannot. Documentation you write for a colleague turns out to be documentation the agent needs too.
